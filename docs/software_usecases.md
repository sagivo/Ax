# Software use-case benchmarks

Common shapes a program actually spends time in, measured the same way as `ax bench metrics`: **same algorithm**, **identical printed value**, **fastest of 11 runs** (process spawn included). Ratios below 1.00× mean Ax was faster. A dash means that toolchain was absent.

This file is regenerated by `ax bench software`. The findings log at the bottom is the record of what was slow, why, and what changed.

Toolchains: `cc -O3 -flto -fno-asynchronous-unwind-tables -DNDEBUG`, `rustc -C opt-level=3 -C lto=thin -C codegen-units=1 -C panic=abort`, `go build`, `ax build --tier release`.

## What each row measures

- **loop sum** (`loop_sum`, n=80e6): Accumulate `0 + 1 + … + (n-1)` with wrapping integer add. The basic counted loop.
- **array sequential** (`array_seq`, n=8e6): Push n `u64`s, then sum them in index order. Ax's `for i in range(0, xs.len()) {{ xs.at(i) }}` is in-range, so the check can drop.
- **array random get** (`array_rand`, n=2e6): Fill n `u64`s, then sum n gathers whose index is an LCG. The index is not provably in range the way a `range(0, len)` walk is, so Ax still pays `at`.
- **string join** (`string_join`, n=200e3): Append the two-byte literal `xy` n times and return the length. Idiomatic C/Rust/Go grow a buffer; Ax's only primitive is `str.concat`.
- **map histogram** (`map_hist`, n=2e6): 256 two-byte heap keys, 8192 full walks (2_097_152 increments), then sum. Ax and C use the same chained FNV-1a table (`m.add`); the inner walk is `range(0, keys.len())` so `at` is in range. Rust is `HashMap`, Go is `map[string]int64`.
- **sort integers** (`sort_ints`, n=400e3): Fill n `i32`s from an LCG, stable-mergesort them, checksum `Σ xs[i]*(i+1)`. Same mergesort in every language. `sort(..., i32.cmp)` lowers to `ax_rt_sort_i32` (no trampoline).
- **file read** (`file_read`, n=67e6): Checksum a 64 MiB file. Ax `io.bytesum_file` mmaps in place; C does the same mix over `mmap`; Rust and Go use the idiomatic `read_to_end` / `os.ReadFile` copy.
- **file write** (`file_write`, n=4e3): Overwrite a file 4_000 times with a 128-byte payload. Measures open/write/close, not string building — `io.write_file` is the Ax primitive.
- **HTTP GET** (`http_get`, n=400): 400 keep-alive GETs of a 16 KiB body from a local server, checksummed with the same mix. Ax uses the `axrt` pool; the others hold one TCP connection and parse Content-Length themselves.

## Findings log

### Pass 0 — harness (no numbers yet)

Stood up `ax bench software` and this document. Nine use cases, four languages,
identical-output gate. Existing `ax bench metrics` already covers loop-carried
compute, arenas, and mmap IO; this suite is the *software* shapes those kernels
are not: sequential/random arrays, string building, maps, sort, file write, HTTP.

Known defects *before* the first timed run, from reading the runtime:

- `Map` is a singly-linked list (`ax_rt_map_insert` walks `m->head`). That
  cannot match `HashMap` / Go `map` / a bucketed C table. First optimisation
  candidate if `map_hist` loses.
- `str.concat` always allocates a fresh buffer. C `realloc`, Rust `String`,
  and Go `strings.Builder` grow in place. First optimisation candidate if
  `string_join` / `file_write` lose.
- `sort` is a stable mergesort by language rule (oracle ≡ native). `qsort` is
  not stable and Rust's `slice::sort` is a different algorithm. A loss here
  may be the stability tax, not codegen. Recorded as such if it happens.

### Pass 3 — one-walk `m.add`, specialised `sort_i32`, fair C map

- **`m.add(k, d)`** is one hash + one walk: find-or-insert, then add. The
  histogram no longer does `get` then `insert`.
- **C `map_hist` uses the same FNV-1a chained table** as Ax. Pass 2's C
  column was a 256-slot table with inline 2-byte keys — a different
  algorithm, the same class of mistake as the old `primes` row.
- **`sort(..., i32.cmp)` lowers to `ax_rt_sort_i32`**: the same ping-pong
  mergesort with an inline `<=`, no `Ordering` trampoline.

The hash table, in-place concat, `reserve`, and shared mergesort from
pass 2 stay. The unsound `at(i % n)` proof was dropped.

### Pass 4 — 15% slop; header-inline of `map.add` reverted

- **The 5% "behind" band flipped `loop_sum` between runs** because spawn
  is 1.5–2.6 ms of a 1.6 ms sample. Raised to 15%.
- **A header-inline `ax_rt_map_add` broke Cranelift** (no symbol to
  resolve) and a C-backend-only inline made the row *worse* (11.2 ms
  vs 10.9 ms) — extra null checks around a two-byte walk. Reverted.
  Cranelift and C both call `ax_rt_map_add`.
- **C `map_hist` now takes `AxStr` keys** (pointer + runtime length),
  same as Ax. A leftover 2× after that is the call + SSA spill around
  the walk, not a different table.
